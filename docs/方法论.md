# 给 Agent / 模型设计者的三条启示

这个项目本质上是一个 Agent 系统。它跑了 19 个版本，前 18 版的核验全部通过，
**第 19 版才发现真 bug**。这个过程中暴露的三条问题，值得所有做 Agent 的人写下来。

---

## ① 验收环境必须与真实使用环境一致

### 发生了什么

第 1 到 18 版的每一次核验，都在 **1000×1600** 的无头浏览器窗口里跑。
这个窗口比页面内容（≈930px）高，所以页面完整显示，**每一步的测量都是对的**。

真实用户在 **690×736** 的窗口里看。页面用了最常见的垂直居中写法：

```css
html,body { height:100% }
body { display:flex; align-items:center; justify-content:center }
```

内容比窗口高 194px，居中导致**上下各溢出 97px，而上面那截滚动不回去**
（这是 flex 居中溢出的经典陷阱：溢出部分是"不可达"的）。

结果：浏览器把卡片顶端切掉了 31px，恰好切在 logo 顶部下方。
用户看到的现象是「logo 顶部和边框重合」——一个看起来像版式 bug 的视觉问题。

Agent 检查了 18 次，全部报告"间距 14.50px，与左右下完全一致"。

### 为什么这是个系统性问题

**Agent 的测试环境总是比生产环境干净。**

| 差异来源 | 本例中的表现 |
|---|---|
| 窗口尺寸 | 测试 1000×1600，生产 690×736 |
| 浏览器 chrome | 测试无（headless），生产有标签栏 |
| 缩放比例 | 测试强制 dpr=1，生产 dpr=1.25 |
| 字体 | 测试无，生产系统字体 |

这些差异在测试里**一个都不会暴露**，因为它们需要真实环境才会显现。

### 怎么做

**方案一：让测试环境覆盖真实约束。**
```python
for w, h in [(1000,1600), (690,736), (560,600)]:
    shot(html, w, h)
    assert_no_clipping(...)
```
本仓库的 `tools/verify_boundary.py` 就是这么做的 —— 它不只测一个窗口。

**方案二：至少在报告里写清测量条件。**

报告不是"测试全部通过"，而是"在 1000×1600 headless 窗口下测试全部通过"。

**后者一句话的成本，但能省掉一次线上事故。**

## ② 多周期 / 多状态系统，只验一半等于没验

### 发生了什么

实心文字层用 `pr` 驱动，粒子层用 `1 - pr` 驱动。两个不同时钟。

```
第一周期（ci=0）：
  pr 从 0 走到 1，两层恰好同步 → 一切正常

第二周期（ci=1）：
  pr 从 1 走到 0，两者关系翻转 → solidA = 1，旧字被画了出来
```

之前的每一轮核验**只看第一个周期**。第一周期是正确的，所以所有测试都过。

这个问题在代码里潜伏了三个版本，直到用户说「旧字体变化成新字体时，旧字体没有彻底消失」才暴露。

### 根因

**"我测了"和"我测全了"是两件事。**

对于有状态、有周期、有分支的系统，单次通过率没有意义。
需要覆盖的是**完整的状态空间**：

| 系统类型 | 至少要覆盖 |
|---|---|
| 周期性动画 | **完整周期的每一段**，尤其首尾衔接处 |
| 有分支的状态机 | 每条可达路径 + 每条路径的终态 |
| 响应式布局 | 尺寸区间的**边界值**，不是中间值 |
| 随机/抖动动画 | 多个随机种子，或改为确定性快照 |

### 怎么做

**验收脚本要显式遍历状态，而不是采样。**

本仓库的时间轴验证覆盖 `v ∈ {0.02, 0.06, ..., 0.90}` 共 14 个点，
且**包含两个粒子位移峰值时刻**（v≈0.18 与 v≈0.82）—— 只测中间值会漏掉极值。

另外，**首尾衔接必须单独测**。本仓库测空场时，
v=0.43 差异 30826 px、v=0.44 掉到 10 px，一帧之间完成消散。
这种陡峭的边界只用区间中点测是测不出来的。

## ③ 指标本身要先验证有效性

### 发生了什么

用户要求：「应该以『AI时代的』的飞散幅度为基准，改一下『灵感指南』」。

我设计了三个指标，测出三个不同的结论：

| 指标 | 定义 | 测出的 A/B | 问题 |
|---|---|---|---|
| A | 粒子到文字轮廓的平均距离 | 0.875 | 笔画密的那段，粒子飞出去仍落在字形范围内，被算成"没飞" |
| B | 散开面积 = 粒子像素面积 ÷ 字形像素面积 | 0.768 | 分母受 alpha 阈值影响，密笔画被阈值吃掉更多像素 |
| C | 位移幅度 = 粒子云外接范围 ÷ 字形外接范围 | **1.001** | ✓ 正确 |

**指标 A 和 B 都说"两段不一致"。** 如果当时直接照着结论去改，
会去修一个**本来正确的公式** —— 因为实际 bug 是一个藏在系数里的 `× 0.36`，
且早就修好了。

指标 C 还暴露了一个更隐蔽的陷阱：**采样窗口选错会测出"完美"的假象。**
v < 0.18 时实心字还在屏幕上，粒子云的外接框与字形完全相同，
扩张比恒为 1.000 —— 一个看起来标准答案的、毫无信息量的数字。

### 怎么判断指标是否可信

**问一句：它会不会被无关因素影响？**

想测的量是「飞了多远"。那么这些因素**不该**影响它：

- 笔画疏密 ← A 受影响了
- 粒子密度
- alpha 阈值 ← B 受影响了
- 当前是否还有实心字 ← C 在错误窗口下退化成常数

任何一个"不该影响却在影响"，就是指标被污染的信号。

### 怎么做

**对关键指标做一次反向验证：故意制造一个已知答案的场景，看指标能否检出。**

本仓库的 `tools/verify_amplitude.py` 就是这个思路的产物 ——
它不只测当前状态，而是**同时跑正确指标和错误指标，把失真过程摆在输出里**。

## 三条启示的共同点

这三条指向同一件事：

> **自动化系统的失败，往往不是"没做"，而是"做了但测的不是你以为的那个东西"。**

- ① 是**环境不对** —— 测的地方不是你运行的地方
- ② 是**样本不全** —— 测的不是完整的状态空间
- ③ 是**指标不对** —— 测的不是你关心的那个量

三者都属于同一个类别：**验证的有效性**，而不是验证的数量。

再多跑 100 遍错的测试，不如先花 5 分钟确认这个测试在测什么。
